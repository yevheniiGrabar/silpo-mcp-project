# КОНЦЕПЦІЯ (зафіксовано) · «Останній Шанс» (Last-Chance Engine)

> ⚠️ ПІВОТ: це нова головна концепція проєкту (замість meal-planner). Документи 00-08 описують попередній meal-planner і вважаються ВТОРИННИМИ, доки не вирішено, чи переспрямовувати збірку. Цей файл — джерело істини по продукту.

## 1. Суть (one-liner)
Агент зшиває **два дедлайни в один checkout**: персональний бонус/купон гостя, що **згорає сьогодні**, оплачує **уцінений near-expiry товар**, який Сільпо от-от спише. «Дві смерті → одна вечеря».

## 2. Killer-властивість (чому це сильно)
Це єдина механіка, де **економія клієнта = ПРЯМЕ скорочення двох статей збитку рітейлера одночасно**:
1. **Списання** свіжого товару, що псується (near-expiry).
2. **«Мертве» купонне/бонусне зобовʼязання** на балансі лояльності.
→ Тому цінність **доводиться прямо на живих даних MCP**, без A/B, без гіпотез про готовність платити, без вигаданих цифр. Це закриває карточку «Валідація цінності», де більшість команд провалиться.

## 3. Проблема + для кого (карточка 03)
- **Гість:** у нього тихо згорають бонуси/купони (не пам'ятає, не встигає), і він переплачує за повноцінний товар, коли поруч є вигідна уцінка.
- **Сільпо:** щодня списує товар, що не продався до кінця терміну, і носить на балансі непогашені купонні зобов'язання.
Обидві болі закриваються однією дією.

## 4. Агентний сценарій (карточка 02) — послідовність дій через MCP
> Дотримуватися перевірених фактів із `docs/06`: спершу резолв контексту (branch → deliveryType → ДОСТУПНИЙ слот), кошик — лише активний гостьовий, checkout = поля checkoutWebLink/MobileLink.

1. **Резолв контексту:** `silpo_list_branches` → deliveryType → `silpo_get_time_slots` (available:true).
2. **Зібрати «горючі» стимули:** `silpo_get_my_coupons` (+`get_coupon_details` для дат), `silpo_get_my_promos`, `silpo_get_loyalty_info` (бонусний баланс), `silpo_get_my_certificates` → відібрати ті, що згорають ≤ N днів.
3. **Знайти «горючу» вигоду:** `silpo_get_promotions` → `silpo_get_products(promotionCode, mustHavePromotion, sortBy=price)` → взяти найглибші уцінки як **proxy near-expiry** (див. ризик нижче).
4. **Матчинг (детермінований):** спарувати «горить бонус × горить уцінка × реальна потреба» — потребу беремо з `silpo_get_my_offline_orders`/favorites (що людина реально купує). Порахувати **ефективну ціну після застосування бонуса**.
5. **Зібрати кошик:** мутація активного кошика `silpo_add_or_update_cart_products` → `silpo_get_shopping_cart_by_id` (тотали, validations[], checkoutWebLink/MobileLink).
6. **Віддати «рятувальний лінк»:** TG-повідомлення з таймером «обидва згорають опівночі» + сума «−X₴ списань + погашено Y₴ зобов'язань».
> Safe-default: нічого не купується без явного тапу гостя (MCP не має справжнього кошика/оплати).

## 5. Бізнес-модель + KPI (карточки 05/06)
- **Всередині Сільпо (growth/retention-фіча) з жорсткими KPI:** ↑ redemption купонів (менше «мертвих» зобов'язань), ↓ ₴ списань на matched-SKU, ↑ частота візитів.
- **Опційний споживчий Pro-шар:** миттєві алерти про найглибші уцінки біля дому.
- **Валідація — рахується прямо:** врятований товар × маржа + погашене зобов'язання; A/B на redemption rate.

## 6. Канали / інтеграції (карточка 05)
- **TG-бот** — головний канал «рятувальних» лінків з таймером (віральність, скріншот).
- **B2B-дашборд** для категорійних менеджерів Сільпо: redemption-rate, sell-through уцінки, ₴ скорочених списань по SKU.

## 7. 6 карток-критеріїв — чек
- **01 MCP✓** — coupons/promos/loyalty/certificates + promotions + products + cart/checkoutLink.
- **02 Агентний✓** — збір стимулів → matching «горить×горить» → перевірка наявності → мутація кошика → лінк.
- **03 Проблема✓** — згораючі бонуси гостя + списання/мертві зобов'язання Сільпо.
- **04 Demo✓** — live-MCP-скрипт на реальному акаунті (код не обовʼязковий, але тут дешевий і переконливіший за слайд).
- **05 Інтеграція✓** — лояльність Сільпо + TG + B2B-дашборд.
- **06 Валідація✓** — economics рахується на живих даних (врятований товар × маржа + погашене зобов'язання).

## 8. План демо (код НЕ обовʼязковий)
Live-MCP-скрипт (Python/Node, вже маємо робочий raw-клієнт) на 2-3 підготовлених акаунтах:
1. get_my_coupons+promos+loyalty+certificates → підсвітити стимули, що згорають ≤3 дні.
2. get_promotions → найглибші уцінки як proxy near-expiry.
3. matching → ефективна ціна після бонуса + потреба з офлайн-чеків.
4. мутація кошика + реальний checkoutWebLink.
5. TG-картка з таймером. На екрані журі — справжній лінк + цифра «2 збитки Сільпо → 1 вечеря».
Опційно: Figma-макет TG-картки поверх скрипта.

## 9. ⚠️ Чесні ризики / залежності (винести на стіл, не ховати)
1. **Near-expiry — proxy:** MCP НЕ віддає структурованих дат придатності. У демо near-expiry = найглибші поточні уцінки (`get_promotions`). Справжня anti-waste версія потребує внутрішнього фіда Сільпо (прапорець near-expiry/дата списання по SKU) — це залежність, не готова фіча. Назвати чесно.
2. **Breakage-конфлікт:** частина купонів свідомо розрахована НЕ бути погашеною (breakage = прибуток лояльності). Форсування redemption — бізнес-розмова з Сільпо, виносити відкрито, не як чистий win-win.
3. **Demo-акаунт:** потрібен акаунт із гарантовано «палаючими» купонами/бонусами + історією + активним кошиком. Заздалегідь підготувати (свіжий тестовий — порожній).
4. **MCP без історичних цін** → НЕ будувати месседж на «твоя інфляція / окупність». Тільки поточні дані.

## 9б. Ринкова валідація + докрутки (ресерч US/EU + UA, 32 веб-пошуки)
**Сильний прецедент-заход:** Сільпо у 06.2026 інтегрувало сторонні транзакції (квитки, «Каса вражень») ВСЕРЕДИНУ «Власного Рахунку» й приймає там оплату → заходити як розширення «Власний Рахунок = маркетплейс пропозицій», не як окремий food-waste проєкт (знижує орг-барʼєр).
**Валідує:** coupon-expiration FOMO (наукою), breakage 12-30% бонусів (мертве зобовʼязання), near-expiry markdown (Flashfood −27% shrink/+72% візитів/$56M), укр.покупець раціональний+купон-орієнтований.
**Чого хочуть клієнти:** автоматизувати рутину «сортувати купони за терміном» (прямий попит саме на це), гіперперсоналізація «мій бонус+релевантний товар зараз», ОДИН клік без екранів умов.
**ОБОВʼЯЗКОВІ докрутки під реальні барʼєри:**
1. НЕ брендувати як «врятуй товар зі списання» (репутаційний барʼєр рітейлу) → подавати як ОСОБИСТУ вигоду: «твій бонус + супер-ціна на твій ЗВИЧНИЙ товар».
2. Пушити ТІЛЬКИ товари з привичної корзини (get_my_offline_orders) — urgency підсилює наявний намір, не створює новий.
3. UX = один клік «знижка застосована», без пояснень умов (уникати coupon-fatigue).
4. Подавати як ГІПОТЕЗУ для пілоту (вузька категорія хліб/молочка) + власні дані конверсії — прямого бенчмарку «два дедлайни разом» у світі НЕМАЄ.
5. Чесно проговорити moral-hazard (Berkeley Haas): «економія = −2 збитки» не гарантована 1:1 — журі це поважає.
**Оговірка даних:** майже вся кількісна база — US/EU з маркетинг-блогів (цифри розходяться 4-5×); укр/Silpo-специфічних near-expiry даних немає.
